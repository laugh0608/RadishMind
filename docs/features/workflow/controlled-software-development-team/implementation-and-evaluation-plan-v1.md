## 建议的首个验证任务

首个任务已固定为仓库内独立合成 Go 模块，见[任务说明与冻结计划](../../../../scripts/eval/fixtures/development-task/README.md)。只创建基准 / 候选副本，不让任务修改 RadishMind 工作树或其他项目；阶段 2 再引入 React / TypeScript。合成缺陷不代表平台现存缺陷。

| 使用阶段 | 任务 | 验收依据 |
| --- | --- | --- |
| 阶段 0 至 1 | 修复示例只读任务列表接口的筛选 / 边界缺陷，补齐回归用例 | 故障在基准可复现；修复后正常、空结果和非法输入用例通过，未改动授权路径外文件；提交可审阅 patch 与实际执行证据 |
| 阶段 2 | 在该示例增加只读任务状态接口与前端状态面板 | 先确定接口 / 类型 / 错误语义，再由 B / C 实现；D 验证正常、空与失败状态，R 审阅同一集成版本 |

创建试验仓库前固定基准提交、依赖 / 镜像、允许路径、命令档案与输出摘要。固定响应可驱动工具调用验证实际文件和测试行为；合成任务通过只证明技术链，不作为真实开发质量或团队收益证据。

## 阶段 0：方案、契约与选型验证

当前已完成主 / 子专题、现有边界核对、三文件代表任务、探针计划 / 工具请求合同和离线准备 CLI；人工修正候选后 8 项测试通过，独立候选镜像内 7 项 SDK LLM 契约测试通过。阶段 0 尚未完成，以下继续推进：

1. 复用已固定的合成 Go 基准、需求、允许路径和验收命令，将真实 SDK 工具输出、测试结果与同一候选摘要绑定；当前人工修正及离线摘要不代替正式交付格式。
2. 按已冻结的[尝试控制合同](../../../contracts/development-attempt-control-v1.md)，实现持久尝试 / 提议 / 事件事务、当前资格读取、专属监听器 与 SDK 固定响应接线，再验证实际 Agent 取消和隔离工具。SDK 依赖和本次离线容器窗口已完成，后续服务 / 沙箱按具体范围授权。
3. 单尝试委托、预留 / 回执、权威事件与工具参数已物化；继续明确团队资源、角色权限、开发产物保存 / 下载与保留，完成实际存储方案。
4. 按[UI 子专题](collaboration-workspace-ui-v1.md)完成任务流程、失败状态与设计等级评估，并取得对应视觉设计依据。
5. 在[集中任务卡](../../../task-cards/development-task-probe-v1-plan.md)连续记录兼容性、正反例和停止线，确定单 Agent 交付范围；不为五个角色分别建卡。

进入阶段 1 前，采用框架的关键试验有证据、具体依赖与运行影响明确，执行 / 数据 / 权限合同和实现范围获得确认。只有文档存在、SDK 官方示例可运行或工作台容器通过，均不足以替代这些条件。

## 阶段 1：单 Agent 隔离开发交付

目标是用户在正式 Web 对一个任务发起、取消、审阅并显式保存候选 patch 与测试证据，建立后续团队比较基线。

同一交付范围包含：Go 运行 / 尝试与授权、独立 Python 编码执行器、受限代码容器、Gateway 调用、文件 / 验证工具、产物引用和持久化，以及可用的 Web 操作。按纵向任务连续实现，普通步骤不重复审批。

完成依据：

- 一份固定基准代码经过实际编辑和构建 / 测试，产物与证据绑定同一候选。
- 启动 / 取消权限、模型 / 工具预算、目录和网络边界真实生效。
- 超时、子进程、越界、模型失败、存储失败和结果未知均如实表现。
- 页面刷新与服务重启只恢复记录，不重放模型或命令；显式保存的交付包可精确重读。
- 技术验收使用固定响应时明确标记，不能宣称 Agent 自主完成软件开发或任务效果达标。

初始持久化选择内存测试与工作台所需 SQLite；是否扩展 PostgreSQL 以明确交付需要决定，不为形式上的三种存储同时扩工作量。

## 阶段 2：固定开发团队

在单 Agent 执行边界可靠后，接入 A/B/C/D/R。A 的计划与接口先明确，再允许 B / C 在独立副本有限并行，D 提前准备验收并在集成版本测试，R 在独立上下文审查同一候选，问题进入有上限的定向返修。

完成依据为一个前后端联动代表任务的完整候选交付，覆盖共享契约负责人、依赖拒绝、集成冲突、测试变化 / 过期、独立审查、返修超限与预算耗尽。不能只展示五个角色聊天或分别返回片段。

角色定义和模型映射使用精确版本；团队阶段不默认开放动态组队、递归委派、任意工具、自动合入或新的业务写回。代码容器写授权不能映射成 Action Safety 的 `write_allowed_by_policy`。

## 阶段 3：持续协作与中断处理

在已有基本历史 / 取消 / 保留能力上，完善群聊定向反馈、计划修订、运行间对照、清理、诊断和用户显式创建后续尝试。重读历史与继续执行是不同动作，不能用框架检查点隐式恢复副作用。

完成依据包括长期记录可读取、权限撤销后内容与动作受控、临时材料按期清理、已保存产物保留明确、崩溃后的存活容器和部分产物可核对。未知执行不会被伪装为成功，后续尝试不重复旧影响。

## 阶段 4：真实任务效果验证

恢复真实模型窗口后，用相同基准、任务、验收和预算上限比较单 Agent 与固定团队。先选取 12 项代表任务作为拟定首轮样本：后端修复、前端交互、跨层功能、测试补漏各 3 项；具体任务、许可证、数据和费用窗口在执行前确定，12 项不是已生效基线。

| 维度 | 记录方法 |
| --- | --- |
| 完成质量 | 独立验收通过次数 / 有效尝试次数，记录样本规模、失败类别和未验证项 |
| 错误完成声明 | 未达验收却被报告完成的次数；保留原声明与实际证据 |
| 人工成本 | 澄清、干预、审查和返工耗时 / 次数，区分模型运行与用户等待 |
| 运行成本 | 实际模型尝试、用量来源、估算 / 上报费用、总耗时与预算耗尽 |
| 协作开销 | 冲突、重复修改、无效调用、过期测试和返修次数 |
| 执行边界 | 越界、取消未收敛、未授权调用和失控重试，不能被质量平均值掩盖 |

两种模式分别在独立副本运行，使用相同任务要求和可比资源上限，记录实际模型差异；执行顺序和人工干预也须记录。测试 / 审查独立于开发 Agent 的自报结果，不以批次元数据变化充当代码质量评分。

首轮只建立基线，再决定哪些任务适合团队及扩大条件。不能预先承诺省时比例、通过率提升或生产成熟度，也不因为等待模型新增模型裁判、训练或通用评测平台。

## 当前下一动作与停止线

代表任务、SDK LLM 子合同与单尝试控制合同 / 离线规则已验证。下一步实现持久尝试 / 工具提议 / 事件事务、真实资格读取与专属通道的固定响应接线，继续开发产物合同，再进入完整单 Agent 隔离交付。此文档登记不授权安装依赖、启动 SDK / 容器、调用真实模型、写外部项目或发布产物。待授权的原型试验也不能默认接管现有工作台容器或复用日常数据。

本功能按一条开发顺序推进；真实模型暂停与独立用户验收尚缺的事实继续保留。跨版本回归、团队共享部署、OIDC、计费、长期记忆和通用自治循环均不随本功能自动进入。
