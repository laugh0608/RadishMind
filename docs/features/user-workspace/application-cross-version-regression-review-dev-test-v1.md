# 应用跨版本回归审查（开发 / 测试态）v1

更新时间：2026-10-26

状态：候选，暂不排期；详细契约待设计，未实现。

## 决策与功能目标

本专题在 2026-10-26 较早的方向决策中曾被选为下一主线；全项目复审后，项目所有者批准改以[本机持久工作台交付](local-persistent-workbench-delivery-v1.md)优先，本文转为候选方案。下文边界与实施顺序仅在该候选重新获选后适用，不提供当前开工顺位。

目标仍是让内部开发者修改应用版本后，用相同测试材料审查两版运行差异，并保存人工审查证据。进入条件是持续使用证明逐对查找和整理证据构成实际负担，且测试材料与审查依据明确；尚无独立用户耗时或收益基线，不预填收益。获选后拟先 Workflow、后 Prompt。

## 当前事实与具体缺口

- 既有[评测计划与受控执行专题](application-evaluation-campaign-controlled-execution-dev-test-v1.md)已支持不可变计划、批次、逐项运行、同计划版本配对及 Case / Suite 交接，继续保持完成。
- 当前批次配对要求同一 `plan_id + plan_version + plan_digest`。应用目标版本变化后需要保存新的计划修订，两个修订对应的批次不能直接配对。
- `application_evaluation_handoff.go` 在配对检查后只读取基准批次的一份计划版本，并按该版本的条目顺序读取两侧运行；候选批次中的单一交接记录承载现有 Case / Suite 引用。删除版本相同检查不足以支持跨版本审查。
- 兼容的两版 Definition Run 已能单独进入 Comparison、Case / Suite。本专题补足批量任务中的样本对应、兼容说明和证据交接，不复制运行或比较算法。

## 首轮用户任务

1. 在当前应用中为某个已激活的 Workflow 内容版本保存评测计划并显式执行，保留基准批次。
2. 派生、编辑和审查新的 Definition 内容版本；按现有规则显式激活。
3. 在同一计划中显式采用新目标，检查原样本后保存新的计划修订并执行候选批次。
4. 选择两个已结束的批次，查看两份精确计划、执行目标、样本一致性及不能比较的原因。
5. 对符合条件的逐项 Run 使用既有 Comparison；核对元数据差异与预期分类，显式形成 Case / Suite 证据并记录人工决定。
6. 刷新或重启后能够重新读取两侧计划、批次和已经生成的审查证据；失败或部分交接不能呈现为完整成功。

批次继续各自在目标版本当时活动时执行。查看旧批次不要求旧版本重新激活，也不自动重新运行历史输入。

## 候选首轮范围

| 事项 | 首轮范围 |
| --- | --- |
| 环境与作用域 | 开发 / 测试态，同租户、工作区、环境、应用及现有读取授权 |
| 计划关系 | 同一计划标识的不同修订；不跨任意计划拼接样本 |
| 执行档案 | Workflow 单文本或结构化档案分别比较；不在两种格式间配对 |
| 目标关系 | 同一 Definition 标识的不同内容版本；结构化档案要求输入合同标识与摘要相同 |
| 测试材料 | 条目键、顺序、各项输入、执行参数与预期分类保持一致；实际规范化和身份计算需在详细设计中固定 |
| 执行行为 | 复用既有显式执行、活动目标重验、配额、取消和中断语义；不自动激活、回放、补跑或重试 |
| 审查依据 | 两份精确计划与批次、逐项 Run、既有 Comparison 及人工决定；不新增答案质量评分器 |
| 失败处理 | 明示缺失运行、未完成批次、合同或样本变化、授权失败和交接失败；不跳过失败项制造整批通过 |

模型、路由等实际执行依据的差异必须可见，不能只凭输入相同就宣称所有变量均受控。`changed`、预期分类匹配及元数据变化均不等于答案质量改善。

## 详细设计必须解决的问题

1. **兼容判定与解释。** 两侧精确版本分别读取并验证；固定样本规范化、字段顺序、数值语义、缺失值和摘要规则。区分目标内容版本变化、允许变化的激活依据与不允许变化的合同 / 样本 / 参数。
2. **API 与旧行为兼容。** 明确是否扩展现有配对接口或增加版本化请求，以及严格消费端的升级路径。旧同版本配对、Prompt / Agent / RAG 与 Schedule 已有路径保持原语义；不放宽旧接口后隐式接收新对象。
3. **证据身份与持久化。** 现有候选批次的单一交接锚点能否表达新配对、如何避免旧证据串用、重复提交如何处理、两个批次的版本如何共同绑定、部分写入如何重读，均需明确。复用既有领域所有者，不另建 Run / Comparison / Case / Suite。
4. **权限与历史读取。** 每次预览和交接重验当前作用域、权限与精确引用；历史读取不以重新激活为前提，也不得泄露其他应用资源或返回敏感测试正文。
5. **失败批次与用户决定。** 确定哪些状态只能解释、哪些可产生逐项比较、哪些可以交接；实际失败与不兼容不能被默认分类覆盖。没有完整证据时不允许作出整批通过结论。
6. **页面与设计覆盖。** 在既有 S10 / S6 工作区中表达版本选择、兼容原因、逐项审查和历史证据；按 Family UI 五维评分确定 Pencil 范围，再实现交互与双语界面。

上述问题完成前不修改 schema、API、数据库迁移或配对规则。本轮整体方向决策不等于详细契约已经获批，也不授权启动新服务、安装依赖或调用真实提供方。

## 实施顺序与可验收结果

| 阶段 | 工作 | 完成依据 |
| --- | --- | --- |
| 设计 | 完成上述六项问题、兼容矩阵与具体实施拆分；实际新增协议或持久化边界集中在一份必要的实施任务卡 | 来源事实、允许变化、失败语义、数据归属及迁移策略完整，可评审；不派生同层准入材料链 |
| 后端与存储 | 实现两侧读取、样本一致性、逐项比较组织、显式交接、历史恢复与并发控制 | 定向正反例、权限、幂等、部分失败和旧行为回归；涉及存储时完成内存、SQLite、PostgreSQL 对应验证 |
| Web 产品面 | 实现两版批次选择、兼容解释、逐项证据和人工交接；复用当前任务导航 | 中英文、键盘、等待 / 错误 / 冲突、作用域切换与代表视口符合已确定设计 |
| 连续验收 | 从两版应用与计划修订出发完成运行、比较、交接、人工决定和重读 | 固定响应自动回归、实际浏览器、清理记录与文档一致；独立参与者另记耗时、求助和完成情况 |

阶段是连续开发顺序，不要求每个阶段都创建新专题或新审批入口。只有出现超出已确认设计的协议、权限、依赖或运行范围变化时重新确认；常规实现与范围内验证连续推进。

Workflow 验收后，再设计 Prompt 的模板版本、变量合同和运行时绑定对应关系，复用已证明适用的核心规则。若不能复用，应说明领域差异，不为复用强行统一执行授权或输出语义。

## 验收底线与非目标

- 完整展示基准 / 候选的精确版本、样本对应及失败原因，不把页面列表位置当样本身份。
- 两份计划、批次或运行引用发生不一致时显式拒绝；跨作用域、权限撤销和存储错误失败关闭。
- 保存审查证据需要显式操作；重复或部分失败的结果可审计，不能伪造原子回滚或自动补偿。
- 既有同计划版本配对、Case / Suite 人工决定和各执行档案保留回归证据。
- 不扩跨合同比较、自动样本迁移、自动激活或发布、后台调度、通用评测调度器、模型裁判和业务写回。
- 不从历史 Run 反推输入，不保存提供方原始响应，不扩大结果正文或凭据持久化范围。
- 真实模型试用继续暂停；确定性运行只验证功能与边界，不给出模型质量或生产就绪结论。
