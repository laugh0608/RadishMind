## 文档职责

当前成熟度统一称为“内部开发者预览”。历史 `M3 / M4` 和 `P1` 至 `P7` 编号只用于定位既有证据与长期专题，不再解释为必须逐级晋升的成熟度等级，也不决定今天的开发顺位。当前执行决策以[当前推进焦点](radishmind-current-focus.md)为准，工程整改事实见[工程健康与产品化整改专题 v1](platform/engineering-health-productization-remediation-v1.md)。

## 产品方向

`RadishMind` 是 `Radish` 体系下的 AI 工具、工作流、模型网关和 Copilot 集成平台。它拥有平台自身的本地账户、角色与工作区成员关系，但不替代或复制 `Radish` 自身身份、组织成员关系和业务数据真相源；模型输出默认是解释、诊断、结构化建议或候选动作，高风险动作必须经过人工确认或规则复核。

长期产品面保持四个：

1. `User Workspace`：应用、Prompt、Workflow、Agent / Copilot、RAG、API key、调用量、运行记录和成本摘要。
2. `Admin Control Plane`：本地注册、用户、会话、角色、权限、租户、模型提供方 / 配置档案、模型路由、配额、价格、密钥后端、审计和部署状态；由本地账户模块负责，并可作为 OIDC 客户端接入 `Radish`。
3. `Model Gateway / API Distribution`：OpenAI-compatible / Responses / Messages / Models API 分发、多提供方 / 配置档案 / 模型路由，以及开发测试态配额、价格快照、调用追踪与受控故障回退；生产限流、计费与真实健康状态分别后置验收。
4. `Workflow / Agent Runtime`：提示词、大语言模型、条件与输出节点，以及独立开发测试态 HTTP Tool 与 RAG 执行档案；高风险动作默认要求确认，通用智能体循环继续后置。

图片输入理解与图片生成是横切适配能力，不是第五个一级产品面。图片像素生成继续由独立 `RadishMind-Image Adapter` 与后端承接，主模型只负责理解、规划、约束、审查和结构化意图。

四个产品面共同服务“内部开发者独立创建可复用 AI 应用、受控运行、审查结果与回归验证”。后续优先级由该流程的真实阻塞、维护风险和使用证据决定，不以新增功能、批次或画板数量衡量产品成熟度。

## 后续开发方向（2026-10-26）

全项目复审后，项目所有者批准以“本机持久工作台 → 真实任务效果 → 按需求选择共享交付或业务接入”整合成熟度顺序，替代当天较早的跨版本评测优先方案。2026-10-31 又明确要求将受控软件开发团队纳入下一功能设计，新增功能顺序见下节补充；不把设计登记当作已实现或跳过真实质量验证。一次推进一条实施主线，按可观察结果退出。

### 第一阶段：本机持久工作台

本机交付基座为[本机持久工作台交付 v1](features/user-workspace/local-persistent-workbench-delivery-v1.md)。首轮用户是项目所有者与内部开发者，目标是一次明确配置后在正式 Web 创建 / 打开应用、编辑、受控运行和显式保存结果，关闭重启后继续使用。

- 复用 Go Platform、Python Runtime、React Web、本地账户 / Session 与共享 SQLite；既有 PostgreSQL 实现保留。宿主机先打通同一运行档，Docker 复用配置语义和数据格式；本机容器不等于公开部署。
- 先用既有故障诊断 Prompt 验证完整结果保留，同配置下覆盖 Workflow 版本与运行；不再先增建一个评测产品才能进入交付。
- 收口启动与配置、身份 / 工作区初始化、用户资源、数据目录、正常关闭、错误恢复和备份恢复。详细契约、工作包与验收矩阵集中在一个功能专题维护。
- 退出条件是空环境首次使用、持续使用、重启恢复、备份恢复和关键失败路径经过实际演练；用户可按指南重复完成。已有模块或固定响应测试不能单独证明交付完成。

实施范围已确认，统一运行档、命令、Web 同源接线、独立工作台 Compose 与冷备份恢复已实现；宿主机浏览器主链、冷重启与新目录恢复已于 2026-10-31 验收；`linux/arm64` Docker 构建 / 运行、挂载限制及容器与宿主机备份迁移已验收；独立用户验收仍待完成，保持本阶段未关闭。

### 新增功能方向：受控软件开发团队（2026-10-31）

项目所有者已选择多 Agent 协同的首个场景为受控软件开发团队，并要求纳入正式规划。主专题为[多 Agent 协同与受控软件开发团队 v1](features/workflow/controlled-software-development-team-v1.md)，五个职责子专题承接框架 / Gateway、运行与证据、隔离执行、协作界面和实施 / 评测。

当前按项目所有者继续推进要求实施阶段 0，代表任务与离线探针已落地，SDK 1.59.0 的 LLM 固定响应契约与锁定镜像复建已按本轮授权完成；持久尝试 / 提议 / 事件事务、真实资格与独立回环通道已用固定响应验证。下一步按受限 SDK 工作进程 / 完整事件、代码沙箱 / 归属终止、开发产物合同的顺序推进；真实提供方原生传输仍待验证，通道默认关闭，后续服务须明确运行窗口。工作台独立用户试用暂不安排，继续保留原交付待办，不阻塞本功能开发，也不写成完成。

| 顺序 | 交付目标 | 进入条件 |
| --- | --- | --- |
| 0 方案与选型验证 | 代表任务、框架采用证据、执行 / 权限 / 数据和 UI 合同 | 代表任务、离线准备与 SDK LLM 契约通过；单尝试控制合同及离线规则已验；SQLite 与内部通道已验；完整 SDK / 实际隔离执行与产物待实现，SDK 尚未采用 |
| 1 单 Agent 隔离开发交付 | 在正式 Web 发起、取消、审阅、保存一个候选 patch 与真实测试证据 | 阶段 0 关键条件有证据，实施范围获得确认 |
| 2 固定开发团队 | A/B/C/D/R、有限并行、集成测试、独立审查和有限返修 | 单 Agent 执行边界可靠，接口与共享文件责任明确 |
| 3 持续协作与中断处理 | 定向反馈、计划修订、历史重读、保留清理及显式后续尝试 | 基础持久化 / 取消已有证据，不自动恢复命令副作用 |
| 4 真实任务效果 | 同任务、基准和预算下比较单 Agent 与团队 | 真实模型窗口恢复，任务 / 数据 / 费用明确 |

Go 平台拥有任务权威状态，OpenHands SDK 为编码执行首选候选；单独验证工具往返、委托、取消、事件及预算，不并存多套调度框架。现有 Agent 禁止工具调用且有短调用时限，隔离代码执行与长任务均为拟新增边界，当前尚未实现；旧运行合同不原地放宽。

本方向属于已有 User Workspace 与 Workflow / Agent Runtime 产品面，不新增一级产品面。它不要求先实现跨版本回归审查、团队共享部署、生产密钥或真实 OIDC，也不解锁通用自治、任意工具、业务写回、自动合并 / 推送 / 发布。详细阶段判据只在[实施子专题](features/workflow/controlled-software-development-team/implementation-and-evaluation-plan-v1.md)维护。

### 第二阶段：真实任务与模型效果

真实模型试用继续暂停。恢复后，在已能持续使用的工作台内固定任务集、提供方 / 模型、配置版本、数据和费用窗口，记录结构合规、事实正确、建议有用、人工修改、延迟与可信用量；技术成功、人工浏览器与真实质量分别报告。

- 先使用已有诊断素材和结果审查能力建立基线；现有 Comparison / Campaign 的运行元数据分类不作为答案质量评分。
- 依据失败类型选择提示词、上下文、模型适配或产品流程改进；没有具体问题时不预建模型裁判、训练流水线或新的评测层。
- 退出条件是目标任务有真实使用与人工质量结论，失败与成本可解释，能够据此决定下一笔投入。样本不足时保留限制，不虚构量化收益。
- 模型窗口缺失时可以先完成第一阶段技术工作；完成后明确质量待验证，不自动以新增功能填补等待期。

### 第三阶段：按需求选择共享交付或业务接入

本阶段是选择点，不要求把全部方向依次做完。根据真实使用证据选择一条，并明确替换的排期。

| 方向 | 进入条件 | 交付结果 |
| --- | --- | --- |
| 指定团队环境 | 真实使用者、目标机器 / 网络、负责人和数据要求明确 | 正式 Web / Platform / Runtime 的安装、访问控制、升级、监管与恢复在目标环境演练 |
| RadishFlow 接入 | 实际 UI / command / API 挂载点、负责人、协议与验收环境齐备 | 一个真实业务任务能消费可审查建议；上层业务真相和人工确认边界保持 |
| Radish 联合身份或业务接入 | 真实客户端注册 / 密钥 / 运行资源，或明确业务任务齐备 | OIDC 与业务 Copilot 分别验收，不用上游产品进展推定本项目已接通 |

若真实模型窗口、团队需求或业务挂载点提前齐备，可以明确重排；不自动并行实施多条主线。打包、上传、部署、真实模型和外部操作按当次范围授权。

当前生产密钥后端、环境隔离、进程监管与控制台生产打包（console production packaging）仍为 `not_satisfied`。第一阶段本机可用不等于这些条件已满足，开发身份头也不能成为共享网络的认证方案。

## 当前执行顺位

2026-10-31 已分别按项目所有者明确授权完成宿主机浏览器主链及 `linux/arm64` Docker 构建 / 运行、挂载限制、冷重启和容器与宿主机备份迁移，所属容器、网络和进程均已清理。下一步由独立用户按[运行指南](platform/local-persistent-workbench-operations-v1.md)完成首次与持续使用，记录实际障碍后修复。Windows PowerShell、`linux/amd64` 容器和真实模型仍未验收，不据技术验收关闭全部交付；后续服务窗口仍需各自明确授权。

新功能开发按受控软件开发团队阶段 0 推进；单 Agent 隔离开发交付是其下一实施目标。设计、原工作台独立用户验收与真实模型质量分别记录；尚未采用 SDK 或开放代码工具。

当前动作由[当前推进焦点](radishmind-current-focus.md#接下来事项2026-10-31)维护，细节归[交付专题](features/user-workspace/local-persistent-workbench-delivery-v1.md)。邀请、国际化、定时回归与工程 R2 至 R6 保持完成；`P3 Local Product Shell / Ops Surface` 保持 `local usable / read-only close`，不默认续建旧 Console。历史事实见[能力矩阵](radishmind-capability-matrix.md)与[W44 周志](devlogs/2026-W44.md)。

## 执行节奏与阶段选择

1. 一条产品主线，必要时一条直接支撑它的工程线；每个工作包包含正常路径、失败恢复与可复验结果。
2. 设计与实施记录进入已有对应专题。普通子步骤不另起任务卡、checker 或审批链；确有新协议、权限、存储或运行边界时集中说明影响。
3. 真实故障与安全问题优先处理；必要的浏览器、使用和视觉证据嵌入交付，不以孤立页面或门禁数量代表完成。
4. 普通实现与范围内验证不反复申请同一授权；服务、模型、依赖、发布与外部写入继续遵守明确范围。
5. 阶段结束回写能力事实、剩余缺口和下一选择，不承诺无资源依据的日期，不将历史下一依赖恢复成排期。

## 停止线

- 不把开发测试态数据库、模拟 / 本地适配器、离线冒烟验证、静态模式定义产物、当前本地控制台或部分覆盖率写成生产就绪。
- 不在缺少本地账户 / 会话 / 成员关系负责模块、真实签发方 / 客户端注册、生产数据库资源、密钥后端、部署环境、负责人和发布复核时启用生产能力。
- 不把 Control Plane、Gateway 和 Workflow Executor 混成隐式单体，也不因服务拆分引入新的默认语言栈。
- 不把任务卡、测试夹具、检查器、准入材料或周志当成功能设计文档和当前决策入口的替代品。
- 不继续派生“准入之后的准入”，不把历史下一依赖恢复为当前开发顺位。
- 不在上层项目没有真实挂载点时细化假想接线，不跨工作区修改 `RadishFlow`、`Radish` 或 `RadishCatalyst`。
- 不让模型建议直接写入上层业务真相源，不启用无限制工具、业务写回、自动确认提交或重放。
- 不让模型、客户端或人工批准直接授予 Action Safety 有效级别；v1 不实现 `write_allowed_by_policy`、写方法 Tool、通用动作执行器或新的确认 / 运行 / 审计负责模块。
- 不让 API 密钥、令牌、DSN、提供方原始响应或异常正文进入命令行参数、公开错误、日志或已提交资产。
- 不在缺少评测基线和明确运行窗口时下载模型、长跑真实模型、扩训练 JSONL、蒸馏或权重工作。
