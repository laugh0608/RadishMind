## 产品方向

`RadishMind` 是 `Radish` 体系下的 AI 工具、工作流、模型网关和 Copilot 集成平台。它拥有平台自身的本地账户、角色与工作区成员关系，但不替代或复制 `Radish` 自身身份、组织成员关系和业务数据真相源；模型输出默认是解释、诊断、结构化建议或候选动作，高风险动作必须经过人工确认或规则复核。

长期产品面保持四个：

1. `User Workspace`：应用、Prompt、Workflow、Agent / Copilot、RAG、API key、调用量、运行记录和成本摘要。
2. `Admin Control Plane`：本地注册、用户、会话、角色、权限、租户、模型提供方 / 配置档案、模型路由、配额、价格、密钥后端、审计和部署状态；由本地账户模块负责，并可作为 OIDC 客户端接入 `Radish`。
3. `Model Gateway / API Distribution`：OpenAI-compatible / Responses / Messages / Models API 分发、多提供方 / 配置档案 / 模型路由，以及开发测试态配额、价格快照、调用追踪与受控故障回退；生产限流、计费与真实健康状态分别后置验收。
4. `Workflow / Agent Runtime`：提示词、大语言模型、条件与输出节点，以及独立开发测试态 HTTP Tool 与 RAG 执行档案；高风险动作默认要求确认，通用智能体循环继续后置。

图片输入理解与图片生成是横切适配能力，不是第五个一级产品面。图片像素生成继续由独立 `RadishMind-Image Adapter` 与后端承接，主模型只负责理解、规划、约束、审查和结构化意图。

四个产品面共同服务“内部开发者独立创建可复用 AI 应用、受控运行、审查结果与回归验证”。后续优先级由该流程的真实阻塞、维护风险和使用证据决定，不以新增功能、批次或画板数量衡量产品成熟度。

## 能力建设顺序

以下是职责与依赖顺序，不是仍待从头实施的清单；已完成事实见[能力矩阵](radishmind-capability-matrix.md)。

### 1. 平台与协议基座

- 统一规范契约、模型服务、模型网关、提供方 / 配置档案和基础评测。
- 保持结构化 JSON、失败关闭、密钥脱敏和上层业务真相源只读边界。
- 历史 `P1 Runtime Foundation`、`M3` 和 `M4` 证据继续可复验，但不再扩同层准入链。

### 2. 工作流与用户闭环

- 优先完成 Workflow 草案创建、编辑、校验、保存、恢复、审查和安全执行。
- 运行历史、失败诊断、对比、评测用例 / 基线 / 套件与模型网关请求审查形成连续产品链。
- 用户工作区应用接入、配置草案、发布治理、应用目录和 API 密钥生命周期按真实使用路径验收。

### 3. 开发测试态持久化与身份边界

- RadishMind 自有运行数据允许使用明确命名的 SQLite / PostgreSQL 开发测试态存储库。
- 迁移、作用域、原子并发、重启恢复、运行角色和不回退语义必须有可执行证据。
- 先完成本地账户、会话、角色与工作区成员关系，再完成确定性 OIDC 依赖方；真实 Radish 联调与生产认证仍必须等待上游客户端注册、密钥、部署资源和负责人。

### 4. 运行时与工程治理收敛

- 模型网关使用受控 `stdio` 工作进程池，保留显式进程回滚模式。
- 测试、覆盖率、性能预算、PR / 发布持续集成与仓库门禁按风险分层维护。
- 入口文档、活动检查器、测试夹具和任务卡必须回到各自职责；历史证据可索引、可手工复验，但不占当前主线。

### 5. 外部接入、生产化与模型适配

- `RadishFlow` 优先于 `Radish`；真实挂载点、负责人、协议和验收环境明确后再恢复接入。
- 生产密钥、环境隔离、进程监管、配额 / 计费、生产 API 密钥和公开生产声明分别验收。
- `RadishMind-Core` 采用开源基座加自有协议、数据与评测偏好适配；没有评测和运行窗口时不启动训练或长跑。

## 后续开发方向（2026-10-26）

项目所有者授权决定整体方向后，后续开发选择“应用版本迭代与回归评测 → 内部环境交付 → 真实任务与业务接入”为推进顺序。当前成熟度仍为内部开发者预览；各阶段完成以可用能力和对应验收证据为准，不按功能数量或预设日历晋级。

### 第一阶段：应用版本迭代与回归评测

- 当前主线为[应用跨版本回归审查](features/user-workspace/application-cross-version-regression-review-dev-test-v1.md)。先完成 Workflow，再在核心规则验证后接入 Prompt；两者串行推进，不同时扩展所有执行档案。
- 用户应能用相同测试材料审查同一应用两版的运行差异，查明不兼容或失败原因，并保存可追溯的人工审查证据。
- 工作覆盖领域契约、精确版本与样本对应、必要的持久化、严格 API、Web 比较与交接、历史读取及完整验收；当前实现仍只支持同计划版本批次配对。
- 退出条件是跨版本审查的正常与失败路径、旧功能兼容、适用的双数据库与中英浏览器证据成立。独立体验补充完成情况、耗时和求助点，不用自动化替代，也不阻塞此前可以独立完成的设计和代码工作。

### 第二阶段：指定内部环境的安装、升级与恢复

- 在首阶段能力稳定后，选择一个明确内部运行环境与负责人，面向正式 Web、Platform 与 Runtime 完成安装配置、持久化、进程监管、日志脱敏、备份恢复及升级回滚。
- 先确定单机 / 团队访问范围及其身份、凭据、网络和数据要求。开发测试身份不能因为被打包就用于共享或生产环境；缺少部署目标时先停在具体设计，不制造虚假部署完成记录。
- 退出条件是目标环境可重复安装、重启保留数据、升级与恢复经过实际演练，运行依赖和未满足的生产条件可审查。打包、上传和部署按当次明确范围另行授权。
- 当前生产密钥后端、环境隔离、进程监管与控制台生产打包（console production packaging）仍为 `not_satisfied`；将交付列入路线图不改变这些事实，也不默认扩大本地控制台范围。

### 第三阶段：真实模型验证与 RadishFlow 业务接入

- 真实模型试用仍暂停。恢复后先固定一个任务集与明确的提供方 / 模型、数据和费用窗口，记录结构合规、事实正确、建议有用、延迟与用量，再依据结果选择适配或质量改进。
- 第一个上层业务接入仍优先 RadishFlow，限定一个实际入口和可审查的建议输出；真实挂载点、负责人和验收环境齐备后设计并实施。不改变上层业务真相源，不自动写回。
- 真实提供方或业务挂载点先于前一阶段齐备时，可以重排到下一工作窗口，但须明确替换哪项排期，不默认并行开多条主线。相关条件持续缺失时，继续已经具备条件的本地能力建设，不反复追加准入文档。

### 后续专项的进入依据

| 方向 | 决策 |
| --- | --- |
| 图片生成后端与产物交付 | 保留为后续独立能力；只有具体图片任务、后端、运行资源和数据 / 安全边界明确后排入主线，不仅因存在 adapter 就续批 |
| 账户恢复与 MFA | 随内部共享访问的风险和恢复需求评审；先确定身份核验与恢复渠道，不先做无可信恢复源的页面 |
| Gateway 限流、真实降级与计费 | 按真实调用量、故障和交付要求分别进入，复用当前请求追踪与配额，不为功能齐全预建计费账本 |
| Agent 循环、长期记忆与模型训练 | 继续后置；分别需要具体任务、受限执行 / 数据策略、质量基线和资源窗口，不随版本评测自动开放 |
| 后端领域拆分与性能优化 | 有当前功能维护或性能证据时随主线解决，不建立无问题依据的独立重构队列 |

2026-10-21 的 Prompt / Workflow 编辑与恢复、2026-10-26 的首次使用指引和悬停修正保持完成。邀请、中英国际化、定时回归、工程 R2 至 R6 和本地控制台既有范围不重开；`P3 Local Product Shell / Ops Surface` 保持 `local usable / read-only close`。历史事实分别见[能力矩阵](radishmind-capability-matrix.md)、[W43 周志](devlogs/2026-W43.md)与[W44 周志](devlogs/2026-W44.md)。新专题不是已关闭专题的同层检查续批。

## 执行节奏与阶段选择

1. 一条产品主线、必要时一条直接支撑它的工程线。先做 Workflow，核心机制完成后做 Prompt，再进入内部环境交付准备。
2. 每项功能按设计、后端 / 存储、Web、连续验收推进，交付包含失败恢复和历史读取；按职责形成常规提交，不把可用性工作拆散为互不完整的任务。
3. 实际阻塞与安全问题优先处理；独立体验、局部视觉复核和必要自动回归嵌入主线，不永久替代功能开发。
4. 普通实现与范围内验证不反复申请同一授权。新增协议、权限、依赖、生产声明或运行范围变化先明确影响；服务、真实模型、发布与外部写入仍遵循授权边界。
5. 不预填独立使用或模型质量结论，不承诺尚无资源依据的日期。阶段结束依据用户能力、验证结果和剩余风险决定下一阶段。

## 停止线

- 不把开发测试态数据库、模拟 / 本地适配器、离线冒烟验证、静态模式定义产物、当前本地控制台或部分覆盖率写成生产就绪。
- 不在缺少本地账户 / 会话 / 成员关系负责模块、真实签发方 / 客户端注册、生产数据库资源、密钥后端、部署环境、负责人和发布复核时启用生产能力。
- 不把 Control Plane、Gateway 和 Workflow Executor 混成隐式单体，也不因服务拆分引入新的默认语言栈。
- 不把任务卡、测试夹具、检查器、准入材料或周志当成功能设计文档和当前决策入口的替代品。
- 不继续派生“准入之后的准入”，不把历史下一依赖恢复为当前开发顺位。
- 不在上层项目没有真实挂载点时细化假想接线，不跨工作区修改 `RadishFlow`、`Radish` 或 `RadishCatalyst`。
- 不让模型建议直接写入上层业务真相源，不启用无限制工具、业务写回、自动确认提交或重放。
- 不让模型、客户端或人工批准直接授予 Action Safety 有效级别；v1 不实现 `write_allowed_by_policy`、写方法 Tool、通用动作执行器或新的确认 / 运行 / 审计负责模块。
- 不让 API 密钥、令牌、DSN、提供方原始响应或异常正文进入命令行参数、公开错误、日志或已提交资产。
- 不在缺少评测基线和明确运行窗口时下载模型、长跑真实模型、扩训练 JSONL、蒸馏或权重工作。
