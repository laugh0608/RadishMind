# Agent 协作与执行规则

更新时间：2026-08-22

## 文档目的

本文承接 `AGENTS.md`、`CLAUDE.md` 不适合在每次任务启动时全量加载的协作细则。根入口只保留跨任务、跨阶段且必须立即生效的长期约束；当前阶段仍以[当前推进焦点](radishmind-current-focus.md)为准，技术事实仍以对应专题、契约、代码和验证结果为准。

## 文档职责与优先级

### 三层职责

| 层级 | 职责 | 典型内容 |
| --- | --- | --- |
| Agent 根入口 | 启动即生效的长期契约 | 授权边界、协作原则、核心红线、任务路由 |
| `docs/` 专题 | 稳定但按任务读取的详细规则 | 架构、协议、验证、代码、UI、协作流程 |
| 当前规划与记录 | 随阶段变化的状态和事实 | 当前顺位、临时门禁、“当前不做”、批次证据 |

根入口不是项目手册的副本，`docs/README.md` 也不是阶段规则正文。短入口负责说明“去哪里读”，专题文档负责解释“规则是什么”，当前焦点、任务卡、周志和运行记录负责说明“现在处于什么状态、已经发生了什么”。

### 判断顺序

1. 先遵循项目所有者在当前任务中的明确要求。
2. 再遵循 `AGENTS.md` / `CLAUDE.md` 的启动级约束。
3. 根据任务路由读取当前 `docs/` 真相源。
4. 通过当前代码、契约、配置、测试和验证结果确认实现事实。
5. 文档与实现不一致时，先判断哪一侧过期，再在当前范围内统一修正。

## 任务推进流程

### 开始任务

- 先检查工作区状态，再判断任务属于回答、诊断、设计、实现、验证还是发布。
- 只读取根入口路由到的必要文档；需要追溯事实时再进入周志、任务卡、清单、摘要或运行记录。
- 涉及当前阶段、优先级或下一顺位时，默认先读[当前推进焦点](radishmind-current-focus.md)；不足以判断长期边界时，再读产品范围、路线图、架构或功能专题。
- 回答“下一步做什么”时，先判断应推进哪份功能设计文档，不默认创建新的同层门禁切片。

### 方案与批准

- 用户没有明确要求直接修改时，涉及代码、架构、规则、协议、依赖、评测基线或运行时行为的变更，先说明目标、范围、影响和验证方式并等待批准。
- 小规模、低风险且需求明确的文档、配置或清理变更可以直接实施。
- 不同合理解释会造成明显不同的用户行为、数据模型、兼容边界或外部影响时，先澄清再修改。
- 已批准方案若发生实质性范围变化，应暂停扩张并重新确认，不把变化隐藏在实现细节中。

### 实现与收口

- 优先治理根因和同类问题，避免只修复一个表象后留下重复缺陷。
- 交付小而完整、可复验的纵向切片，不使用占位逻辑或无法覆盖主要使用路径的半成品。
- 不做与当前目标无关的重构；直接影响需求的结构问题应进行边界清楚的必要修正。
- 抽象只服务于真实复用、边界隔离、复杂度下降或契约稳定；简单逻辑不通过多层包装制造间接性。
- 错误处理只覆盖明确的输入、IO、网络、权限、并发和兼容风险，不吞异常、不伪造成功、不用默认值掩盖契约问题。
- 交付时说明完成内容、验证结果和仍未验证的真实风险，不把未执行的运行态验证写成已通过。

## 设计先行与文档分层

- 长期功能、重要页面、跨模块能力或阶段性目标进入代码前，应先确认对应功能专题存在且边界清楚。
- 产品范围、路线图和架构承载方向、阶段、系统职责与长期边界，不承载具体批次流水。
- `docs/features/` 承载产品面和具体功能；`docs/platform/` 承载平台横切能力；`docs/integrations/` 承载外部项目和后端接入。
- `docs/task-cards/` 只承接具体实现批次、前置条件或高风险门禁，不作为产品功能默认主文档。
- `docs/devlogs/`、清单、摘要和运行记录只保存批次事实与验证证据，不作为长期功能设计真相源。
- 普通 UI、文案、布局、只读证据组织和使用性整理默认复用现有测试、构建和聚合门禁。
- 只有新增 API、执行边界、生产声明、schema / 数据格式、外部 provider 风险或高风险能力时，才考虑新增专项任务卡、fixture 或 checker。
- 小规模 bug、低风险文案或样式调整、纯清理和不改变功能边界的验证补漏，不强制新建专题；若暴露文档与实现不一致，应同步修正真相源。

## 授权、运行与工作区边界

### 依赖与环境变更

- 安装或更新依赖、下载模型或数据、写系统目录、修改系统配置、打包、发布或上传前，说明具体命令、目标范围、影响和清理方式，并取得当前任务授权。
- 授权只覆盖已经说明的命令和范围；命令、依赖、版本、写入位置或运行影响发生实质变化时重新确认。
- 构建、测试、类型检查、Lint、静态分析和仓库内常规文件修改可按任务直接执行。

### 服务启动与真实联调

- 真实联调需要启动开发服务器、平台后端或浏览器服务时，默认由用户在本机终端启动。
- 用户明确要求 AI 启动时，先说明命令、端口、预计运行方式和清理方式；启动的后台进程必须在任务结束、提交或交接前关闭。
- 不沿用上一轮或历史会话中的启动状态；真实联调前重新确认本任务所需服务已经启动。
- 普通开发轮次优先使用构建、测试、类型检查和静态检查；真实浏览器联调只在功能或阶段准备验收、用户明确要求，或静态证据不足以判断用户可见行为时执行。

### 沙盒与外部工作区

- 默认先在当前沙盒和 RadishMind 工作区内执行；权限、网络、证书或 PATH 限制导致必要验证无法取得真实结果时，再申请最小范围授权。
- 提权不扩大任务范围，也不替代依赖安装、服务启动、发布或外部写入所需的明确授权。
- 本任务临时提供的外部仓库路径只用于只读参考，不写入长期文档，也不据此修改外部项目。
- 未经明确要求不执行破坏性 Git 操作，不跨工作区编辑 `RadishFlow`、`Radish` 或 `RadishCatalyst`。

## 本地模型脚本协作

- 长时间运行、显著占用 CPU / GPU / 磁盘或加载本地模型权重的脚本，默认由用户在本机终端执行。
- 要求用户执行前，必须给出完整可复制命令，包括适用的 `--manifest`、`--provider`、`--model-dir`、`--sample-id`、`--output-dir`、`--summary-output`、`--sample-timeout-seconds`，以及是否启用 `--repair-hard-fields` / `--validate-task`。
- 用户执行后，AI 负责审计 `tmp/` 下的 summary、候选响应、prompt、audit 或离线评测结果，并据此更新结论、文档和必要提交。
- 运行卡住、超时、中断或只完成部分样本时，先检查已有产物和终端输出，区分模型推理耗时、超时机制、单样本失败和脚本可观察性问题，再决定修改脚本或重跑。

## 验证与留痕

- 每完成一个可分割子步骤，执行与其风险相称的定向验证。
- 日常仓库级验证优先使用 `./scripts/check-repo.sh --fast`、`./scripts/check-repo-fast.sh` 或对应 PowerShell 入口。
- 改动较大、发布前，或影响评测、治理口径、协议、架构、阶段边界与文档真相源时，补跑全量 `check-repo`；快速模式不替代最终门禁。
- 验证和留痕区分开发中、准备合并到 `master`、发布部署三种粒度；发布、上传和部署仍需单独授权。
- 重要阶段性决策除修改代码和专题文档外，还应写入对应周志；长命令输出和实验观察进入摘要、清单或运行记录。

## 文档维护

- 优先更新既有真相源，不为一次性讨论创建散文档。
- 入口文档保持短，只保留定位、当前结论、下一步和明确停止线；历史细节与验证流水进入专题或记录层。
- 根入口软上限为 `180` 行、硬上限为 `250` 行；其它 Markdown 篇幅预算以 `docs/README.md` 和仓库检查器为准。
- 文档中提到外部项目时使用项目名和在线仓库 URL，不写开发者本机路径。
- 架构、协议、目录职责、阶段范围、协作方式或工作流变化时，同步更新对应 `docs/` 真相源和本周周志。

## 根入口维护规则

一条规则只有同时满足以下条件，才应进入 `AGENTS.md` / `CLAUDE.md`：

1. 跨任务成立，而不是某个功能或批次专属。
2. 跨开发阶段成立，不会随当前里程碑自然失效。
3. 必须在读取专题文档前生效，否则容易造成高风险或大范围错误。
4. 无法只通过任务路由和对应 `docs/` 专题可靠承载。

不满足这些条件的内容，应归入专题、当前焦点、任务卡、周志或运行记录。

- 两个根入口必须逐字一致，由仓库基线自动检查。
- 修改根入口时同步检查关联专题是否仍为真相源；修改阶段状态或临时门禁时不反向更新根入口。
- 根入口目标是保持短、稳定和可路由，不汇总所有项目知识。
